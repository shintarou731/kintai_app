### モデル
- **`AttendanceCalendar`（新規）**：月度の期間の決め方。締め日と、締め済みの月度から決める。
  - 締め済みの月度は、締めた時点の期間のまま。
  - 未締めの月度
    - 直前の月度が締め済みなら、開始日は「締め済みの月度の終了日の翌日」。
    - 直後の月度が締め済みなら、終了日は「締め済みの月度の開始日の前日」。
    - それ以外の端は、今の締め日どおり。
  - `containing(date)` は、となりの月度まで調べて、その日を含む月度を返す。
- **`AttendancePeriod`**
  - 期間（start_date・end_date）を外から渡せるようにした。
  - 締めの記録（`closing`）、`closed?`、`adjusted?`（締め日どおりの期間から端を動かしたか）、`ended?` を足した。
  - 前後の月度への移動も、同じ決め方を通る。
- **`WorkRules`**
  - `WorkRules.current` が締め済みの月度も読み込むようにした。
  - `period_containing`・`period_from_param` は `AttendanceCalendar` を通す。
  - 勤怠履歴・予実の確認・ダイアログ・修正申請のリンクなど、既存の画面もすべて同じ期間になる。
- **`MonthlyClosing`（新規）**
  - `close!`：書き込みのトランザクションの中で、次の順に行う。
    1. 勤務ルールと締めを読み直す。
    2. 期間を決める。
    3. 締められるか確かめる（終わった月度か・未締めか・管理者か）。
    4. 全員の値を計算して保存する。
  - `reopen!`：解除する。解除した人・日時を記録する。
  - `rules`：締めた時点のルール。
- **`MonthlyClosingEntry`（新規）**：締めた時点の `MonthlyAttendance` から、値を作って保存する。
- **`ClosedMonthlyAttendance`（新規。`MonthlyAttendance` の子クラス）**：締め済みの月度の勤怠表。
  - 保存した日別の値から作る。今のルールで計算し直さない。
  - 打刻・シフト・休暇も、保存した内容から作る（保存しないオブジェクト）。
  - 遅刻・早退・欠勤の印は、その内容と、締めた時刻で `ShiftCheck` を作って出す。保存した印と一致することを、テストで確かめた。
- **`MonthlyAttendance`**
  - `for_user`／`for_users` は、月度が締め済みなら `ClosedMonthlyAttendance` を返す。
  - 追加したもの：`total_holiday_worked_minutes`・`paid_leave_days`・`absence_leave_days`・`closed?`・`snapshot_data`・`Day#holiday_worked_minutes`。
  - 締め済みの月度では、`correctable?` は false。
- **`MonthlySummary`（新規）**：月次集計の表・合計・警告（退勤漏れ・承認待ちの申請）。
  - 未締めの月度は、今の値（勤怠履歴と同じ計算）。
  - 締め済みの月度は、保存した列をそのまま出す。
  - **F15 の CSV は、ここから読めば画面と同じ値になる**。
    - 従業員別：`rows` の各値。
    - 日別：`row.monthly.days`。締め済みの月度なら、保存した値になる。
- **`ClosedPeriodGuard`**
  - 中身を実装した：`closing_overlapping`・`closed_period_label`・`closed?`・`describe`。
  - 毎回 DB の締めの記録を読む。
- **`AttendanceRecordEditor`（新規・フォームの役割）**：管理者による直接修正・作成・削除。
  - 時刻の解釈と矛盾の確かめは、打刻修正申請（F7）と同じ規則を使う。`AttendanceCorrectionRequest` を保存せずに組み立てて確かめる。
  - 画面を開いた時点の記録の印（`record_token`）と、保存の直前の記録を比べる。違っていれば上書きしない。
- **`AttendanceEdit`（新規）**：直接修正の履歴。

### 書き込みの入口の判定（`ClosedPeriodGuard`）
どの入口も、**書き込みと同じトランザクションの中で** 判定する。SQLite は BEGIN IMMEDIATE で書き込みが1つずつになるので、判定と書き込みの間に締めが割り込まない。

| 入口 | 締め済みの月度にかかるときの扱い |
|---|---|
| 打刻修正申請の申請 | バリデーションでエラーにする。入力画面（`/requests/corrections/new`）も開かせず、勤怠履歴に戻して知らせる。 |
| 打刻修正申請の承認 | `approval_blockers` で止める。承認ボタンは押せず、送っても 422。**承認待ちのまま締めた申請も止まる。** |
| 休暇申請の申請・承認 | 1日でもかかれば、申請・承認ともにエラーにする。 |
| 休暇の取消申請の申請・承認 | 取り消す休暇が締め済みの月度にかかれば、エラーにする。 |
| 管理者の休暇の直接取消 | 既存の `direct_cancellation_blockers` から判定する。フォームを出さず、送っても 422。 |
| 管理者の直接修正・作成・削除 | フォームを出さず、送っても 422。 |
| 打刻（出勤・退勤・休憩開始・休憩終了） | 勤務日が締め済みの月度に入れば、記録しない（下の「決めた扱い」）。 |

却下と取り下げは、勤怠を変えないので止めない。承認待ちのまま締めた申請は、却下か取り下げで片付ける。

## 既知の問題・懸念
- **同時操作の安全性は SQLite の BEGIN IMMEDIATE（書き込みが1つずつ）に頼っている**
  - PostgreSQL などに移す場合は、締めと各書き込みの順番待ち（締めの表のロックなど）を足す必要がある。
  - 既存の承認・取消と同じ前提。
- **締めの解除に理由の入力は無い**（誰が・いつだけを残す）。
- **締めた後のシフトの変更は止めていない**。締めた月度の表示は保存した値なので変わらないが、シフト作成の画面では、過去の締め済みの週のシフトを変えられる。
- **締め済みの勤務日の退勤**：締めた時点で退勤漏れの勤務は、締め済みのまま退勤漏れとして固定される。直すには、締めを解除して直接修正する。
- **直接修正の入力の確かめ**：打刻修正申請（`AttendanceCorrectionRequest`）を保存せずに使っているため、エラーの文言の一部に申請向けの言い回しが残る（例：退勤の空欄のエラー「退勤の打刻を忘れた日は…」）。
- **締めた月度の勤怠履歴で、承認待ちの修正申請の「申請中」の印は今の状態を出す**（数値は固定）。
- **画面の重さ**：月次集計の画面は縦に長い。1280px 前後では、11列の表が詰まり気味。
- 開発 DB のバックアップ `tmp/backup/development-before-sprint-14.sqlite3` を残している（不要なら削除してよい）。
- 開発サーバー＋Playwright での目視確認はしていない。
