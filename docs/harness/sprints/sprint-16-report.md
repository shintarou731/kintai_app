# スプリント 16 実装レポート：アプリ内通知（F16）

## 実装内容

### データ（マイグレーション `20261125210000_create_notifications`）
- 適用前に開発 DB をバックアップした：`tmp/backup/development-before-sprint-16.sqlite3`。`VACUUM INTO` で作り、`integrity_check` は ok。
- テーブルを2つ作るだけで、既存の行は変えない。既存のデータから通知をさかのぼって作ることはしない。適用後、開発 DB の `notifications` と `overtime_alerts` は 0件。
- `notifications`：1件の通知につき、受け取る人は1人。
  - 列：受け取る人・種類・見出し・本文・移る先のパス・操作した人・関連する記録（polymorphic）・既読の日時。
  - 索引：一覧用（受け取る人・日時）と、未読の件数用（`read_at IS NULL` の部分索引）。
- `overtime_alerts`：残業の警告を送った記録。
  - 一意制約：従業員・月度（`2026-11`）・段階（80/100）の組み合わせ。
  - チェック制約：`level IN (80,100)`。

### モデル
| クラス | 役割 |
|---|---|
| `Notification` | 通知1件。種類ごとの表示名と色・未読／既読・`mark_read!`（未読のときだけ書き込む）。移る先のパスはアプリ内だけに限る（`//`・`https:`・`\`・制御文字は保存も遷移もしない）。 |
| `Notifier` | 出来事ごとに、誰に・どんな通知を送るかを決める。`safely` は例外を外に出さず、ログと `Rails.error` に残す。 |
| `OvertimeAlert` | 残業の 80%・100% の判定と、月度ごとに1回だけ送ることの保証（一意制約）。判定と通知の作成を同じトランザクションで行う。 |

### 通知を送る場所（すべて元の処理のトランザクションが確定した「後」に呼ぶ）
| 出来事 | 呼ぶ場所 | 受け取る人 |
|---|---|---|
| 打刻修正・休暇・取消の申請 | 各申請の `#submit` が成功した後 | 有効な管理者全員（申請した本人を除く） |
| 承認・却下（3種類とも） | `ApprovalReview#save` が成功した後 | 申請者 |
| 管理者による休暇の直接取消 | `LeaveDirectCancellation#save` が成功した後 | 休暇の本人（1件。承認待ちの取消申請が処理済みになったことも本文に書く） |
| シフトの公開・変更 | `ShiftWeekPublication#save` が成功した後 | この公開で見えるシフトが変わった本人だけ |
| 有給の付与 | `Admin::Employees::PaidLeaveGrantsController#create` で保存が成功した後 | 付与された本人 |
| 残業の 80%・100% | 退勤（`TimeClock#clock_out!`）、打刻修正の承認、管理者の直接修正（`AttendanceRecordEditor#save`）、勤務ルールの変更（`Admin::WorkRuleSettingsController`） | 本人と、有効な管理者全員（本人を除く） |

### 画面
- **ヘッダーのベル**（`shared/_notifications_menu`）
  - アプリ名と同じ1段目の、ユーザー名の左に置いた。
  - 未読の件数を赤いバッジで出す（100件以上は「99+」）。`aria-label` は「通知（未読 N件）」。
  - 押すと、新しい通知6件の一覧が開く（`<details>`。既存の dropdown コントローラで、外側のクリックや Esc で閉じる）。
  - 一覧の上に「未読 N件」と「すべて既読にする」、下に「すべての通知を見る」を置いた。
  - 375px では、一覧を画面の左右いっぱい（12px の余白）に出す。
- **通知の一覧**（`/notifications`）
  - 新しい順に並べる。各通知に、発生日時（「11/25(水) 17:55（5分前）」。今年でなければ年も付ける）・種類の色ラベル・未読の印・見出し・本文を出す。
  - 「すべて／未読」のタブで絞り込める。
  - 20件ずつのページ分け（「← 新しい通知」「古い通知 →」「1 / 3 ページ」）。範囲外や不正なページ番号は、いちばん近いページにする。
- **通知を押す**：`POST /notifications/:id/reading` で既読にして、関連する画面へ移る（303）。
  - 申請の結果 → `/requests/:id`
  - 新しい申請 → `/admin/approvals/:id`
  - シフト → `/shifts?month=YYYY-MM`
  - 有給 → `/leaves`
  - 残業 → 本人は `/attendances?month=`、管理者は `/admin/monthly/:user_id?month=`
- **すべて既読にする**：`POST /notifications/read_all`。押した画面へ戻る。
- GET で URL を直接開いたときは、既読にせずに一覧へ戻す。

### スプリント15の指摘の修正
1. **ASCII の予備のファイル名**
   - `Content-Disposition` を自前で組み立てるようにした（`AttendanceCsv.content_disposition`）。
   - 予備の `filename=` は `kintai_summary_2026-11.csv` や `kintai_daily_2026-11_unclosed.csv` のような名前になる。`filename*` は今までどおり日本語の名前。
2. **拡張子の制限**：ルートに `format: true, constraints: { format: "csv" }` を付けた。`.json`・`.html`・拡張子なしは 404 になる（ルーティングで確かめた）。
3. **氏名の制御文字**：`User` の氏名に検証を足した。改行・タブ・NUL・U+2028/2029（`\p{Cc}\p{Zl}\p{Zp}`）を拒否し、「氏名に改行・タブなどの制御文字は使えません」と出す。前後の空白と改行は、今までどおり取り除く。開発 DB に該当する氏名が無いことを確かめた。
4. **`Gemfile.lock` の checksum**
   - `bundle lock --add-checksums` を実行した（ネットワークを使った）。
   - `csv (3.3.2) sha256=6ff0c135…bd4e` が入った。ローカルにキャッシュされた `csv-3.3.2.gem` の sha256 と一致することも確かめた。
   - 差分はこの1行だけ。`bundle check` も通る。

## 決めた扱い（仕様で決めるよう求められた点）
- **自分がした操作の通知は、自分には送らない**
  - 自己承認・自己却下、自分の休暇の直接取消、自分への有給の付与、自分のシフトを自分で公開したとき、が当たる。
  - 本人は操作した画面のメッセージで結果を知っているため。
- **管理者が休暇を直接取り消したとき**：本人に送る（種類は「休暇の取消」）。
  - 休暇が消える・有給が戻るという、本人に重要な変化だから。
  - 承認待ちの取消申請が処理済みになった場合も、通知は1件にまとめる。
- **新しい申請の通知（自己承認ルールとの関係）**
  - 有効な管理者全員に送るが、申請した本人には送らない。
  - 有効な管理者が1人だけで、その管理者が自分の申請を出したときは、誰にも送らない。出したのは本人で、ナビの「承認」の件数にも出るため。
  - 有効な管理者が2人以上なら、本人以外の管理者だけに届く（本人は処理できないので、送らないのは自己承認ルールとも合う）。
  - 無効な管理者・無効な従業員には、どの通知も送らない。
- **シフトの公開・変更**
  - 公開の時点で、この公開で見えるシフトが変わった本人だけに送る。
    - 変更・削除が無く追加だけなら「シフトが公開されました」。
    - 変更・削除があれば「シフトが変更されました」。
    - 本文に、追加・変更・削除した日付を書く。
  - 公開済みの週を再公開したときは、変わった人だけに届く（変わっていない人には届かない）。
  - 下書きのまま削除したシフト（従業員に見えていなかったもの）は、通知に含めない。
  - 下書きの保存の時点では送らない（従業員にはまだ見えないため）。
- **残業の警告**
  - 「超えた」は、勤怠履歴やダッシュボードと同じく「ちょうど」を含まない。警告ライン 45時間なら、80% は 36:01 から、100% は 45:01 から。残業時間は勤怠履歴と同じ計算（`MonthlyAttendance#total_overtime_minutes`）。
  - 判定するタイミング
    - 退勤の打刻（勤務日の月度。日付をまたいだ退勤も、出勤した日の月度）
    - 打刻修正申請の承認（却下では判定しない）
    - 管理者の直接修正
    - 勤務ルールの変更。所定労働時間・締め日・警告ラインのどれかが変わったとき、有効なユーザー全員の今月度を判定する。
  - 勤務中（退勤前）の残業の伸びでは送らない。退勤で時間が確定したときに判定する。
  - 締め済みの月度は判定しない。月度の締めの解除では判定しない（過去の月度の通知が急に届くのを避けるため）。
  - 「1回ずつ」は、従業員・月度・段階の一意制約で保証する。記録と通知を同じトランザクションで作る。同時に判定が走っても、後から来た側は一意制約で弾かれて何もしない。
  - 一度に 80% と 100% を両方超えたとき（警告ラインを下げた場合など）は、2件とも送る（80% → 100% の順）。
  - 残業が減って下回り、また超えた場合は、同じ月度には送り直さない。次の月度になれば、また 80% から送る。
  - 月度のキーは `2026-11`（`AttendancePeriod#to_param`）。月度の途中で締め日を変えて期間が変わっても、同じ「11月度」は同じキーとして扱う。
  - 管理者自身の残業は、本人向けの1件だけにした（管理者向けを二重に送らない）。他の有効な管理者には、管理者向けの通知が届く。
- **トランザクションとの関係（失敗しても元の処理は失敗しない）**
  - 通知は、元の処理（承認・申請・取消・公開・付与・退勤・修正・設定の保存）のトランザクションが確定した後に、別のトランザクションで作る。
  - そのため、通知が作れなくても元の処理は取り消されない。また、元の処理が失敗・ロールバックしたときは、通知は作られない。
  - 通知の作成は `Notifier.safely` の中で、`requires_new` のトランザクションで行う。例外は捕まえて、ログと `Rails.error.report` に残し、呼び出し側には伝えない。
  - 1つの出来事の通知（管理者全員分など）はまとめて作る。途中で失敗したら全部作らない（一部の人にだけ届く、ということが無い）。
  - 残業の警告は、通知が作れなければ警告の記録も残さない。次の判定で送り直せる。
  - 元の処理が確定してから通知を作るまでの間にプロセスが止まった場合、その通知は失われる（作り直す仕組みは無い）。下の「既知の問題」に書いた。
- **既読と権限**
  - 自分の通知だけを開ける。他の人の通知の ID を送っても、存在しない通知と同じ扱いになる（「指定された通知が見つかりません」と出して一覧へ戻す）。既読にならず、移る先も明かさない。
  - 「すべて既読にする」は自分の未読だけを対象にする。
  - 画面を開いた時点の最新の通知の ID（`until_id`）までを既読にする。押す前に届いた新しい通知は、未読のまま残す。`until_id` に他の人の ID を入れても、他の人の通知は変わらない。
  - 既読の日時は最初に開いたときのもので、もう一度開いても変わらない。
- **ページ分け**：一覧は20件ずつ、ベルの一覧は6件まで。通知の保存期間の上限（古い通知の自動削除）は設けていない。

## 動作確認の方法
- 起動：`bin/rails server -p 3000`。マイグレーションは適用済み。開発 DB の通知は 0件から始まる。
- ログイン（パスワードはすべて `password123`）
  - 山田 太郎（管理者）：`admin@example.com`
  - 管理 次郎（管理者）：`jiro@example.com`
  - 従業 花子（従業員）：`hanako@example.com`
  - 連打 確認（従業員）：`double@example.com`
- 開発 DB の状態（読み取りだけで確かめた）
  - 有効な管理者は2人（山田・次郎）。
  - 今月（2026年11月）の残業：次郎 1:54、連打 2:05、山田・花子 0:00。警告ラインは 45時間。
  - 承認待ちの申請が5件ある。
- 手順（以下の操作は開発 DB を書き換える。終わったら設定を 45時間に戻すこと）
  1. **新しい申請**：花子でログインし、「申請」から打刻修正を申請する。ログアウトして山田でログインし、ヘッダーのベルに「1」が出ることを見る。ベルを押すと「従業 花子 さんから打刻修正の申請が届きました」が出る。押すと `/admin/approvals/:id` に移り、バッジが消える。次郎にも同じ通知が届いていて、花子には届いていない。
  2. **承認・却下**：山田でその申請を承認（または却下）する。花子でログインし、ベルに「打刻修正の申請が承認されました（日付）」とコメントが出る。押すと `/requests/:id` に移る。
  3. **休暇の直接取消**：花子の承認済みの休暇を、山田が直接取り消す。花子に「休暇が管理者により取り消されました」が届く。
  4. **シフト**
     - 山田で「シフト作成」を開き、ある週に花子と連打のシフトを入れて公開する。2人に「シフトが公開されました」が届く。
     - 花子のシフトだけを変えて再公開する。花子にだけ「シフトが変更されました」が届き、連打には届かない。
     - 通知を押すと `/shifts?month=` に移る。
  5. **有給**：山田で「従業員」→ 花子の有給 → 付与する。花子に「有給休暇が N日付与されました」が届く。
  6. **残業の警告**

## 既知の問題・懸念
- 開発サーバーと手作業のブラウザでは確かめていない（システムテストの headless Chrome だけ）。
- 通知は、元の処理が確定した後に別のトランザクションで作る。その間にプロセスが止まると、その通知は作られない（送り直す仕組みは無い）。SQLite のロック待ちが上限を超えたときも、通知だけが作られない（ログには残る）。
- 残業の警告は、退勤・承認・直接修正・設定の変更のときにだけ判定する。勤務中に残業が伸びている間（ダッシュボードには出る）は送らず、退勤したときに送る。
- ベルのバッジと一覧は、画面を開いたときの内容になる。開いたままの画面には、新しい通知は自動では出ない。
- 99+ のときは、バッジがベルの右上を大きく隠す。375px では、ユーザー名が「従業 花子」程度の長さまでしか見えない（380px 以下では 5.5em で省略）。
- 通知は削除されず、たまり続ける（ページ分けで表示はするが、保存期間の上限は無い）。
- 新しい申請の通知は、申請が取り下げられても残る（押すと、取り下げ済みの詳細が出る）。
- 通知の文言はモデル（`Notifier`）に直接書いている。表示名を変えても、過去の通知の見出しは変わらない（作った時点の文言を保存するため）。
