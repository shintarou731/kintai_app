# スプリント 16.1 実装レポート：F10 の追加分（年5日の印の対象・付与の削除の記録）

## 実装内容

### データ（マイグレーション `20261126090000_add_removal_columns_to_paid_leave_grants`・適用済み）
- 適用前に開発 DB をバックアップした：`tmp/backup/development-before-sprint-16.1.sqlite3`
  - `VACUUM INTO` で作った。`integrity_check` は ok。付与 5件・申請 83件・ユーザー 4件を読み取って確かめた。
- `paid_leave_grants` に列を足すだけ。既存の行は変えていない。既存の付与 5件は、すべて「削除されていない」（`removed_at` が NULL）のまま。
  | 列 | 意味 |
  |---|---|
  | `removed_at` | 削除した日時（NULL なら削除されていない） |
  | `removed_by_id` | 削除した管理者（users への外部キー） |
  | `removal_reason` | 削除の理由 |
- DB の制約：`(removed_at IS NULL) = (removal_reason IS NULL)`。削除の日時と理由は、必ず一緒に入る。
- 適用後、`PRAGMA integrity_check` は ok、`foreign_key_check` は0件。

### 付与の削除を「論理削除」にした
- **物理削除をやめた**。付与の行は消さず、削除した管理者・日時・理由を記録する（`PaidLeaveGrant#mark_removed!`）。付与日・日数・有効期限は、削除した時点のまま残る。
- `PaidLeaveGrant.kept`（削除されていない）と `PaidLeaveGrant.removed`（削除した）のスコープを足した。
- `User#paid_leave_grants` は、削除されていない付与だけを返すようにした。削除した付与は `User#removed_paid_leave_grants` で読む。
- **付与を数えている箇所を、すべて確かめた**（`grep` で `PaidLeaveGrant` と `paid_leave_grants` を全件見た）。
  | 箇所 | 対応 |
  |---|---|
  | 残日数・ホーム・休暇画面・休暇の詳細・従業員の編集・通知の本文（`PaidLeaveAccount.new(user)`） | `user.paid_leave_grants`（kept）を使う |
  | 従業員一覧（`PaidLeaveAccount.for_users`） | `PaidLeaveGrant.kept` |
  | 申請・承認の残日数の確かめ（`LeaveRequest#paid_leave_shortfall`） | `PaidLeaveGrant.kept` |
  | 削除の確かめ（`PaidLeaveGrantRemoval#shortage_increase`） | `PaidLeaveGrant.kept` |
  | 管理者の付与の画面（`load_account`） | kept と、履歴用の削除した付与 |
  | 計算の本体（`PaidLeaveLedger`） | 念のため、削除した付与が渡されても `reject(&:removed?)` で数えない |
  | 月次集計・CSV（F14・F15） | 付与ではなく休暇から数えているため、影響なし（確認のみ） |
  | 通知（F16） | 付与の通知の `subject` は、付与の行が残るので、そのまま参照できる |

### 削除の操作（管理者）
- 付与の一覧の「削除」を押すと、**確認画面**（`/admin/employees/:id/paid_leaves/:grant_id/removal/new`）が開く。
  - 画面の内容
    - 削除する付与：付与日・日数・有効期限・使用と残り・登録者
    - 削除後の残日数：「残り 10日 → 残り 0日」と、申請できる残りの変化
    - 削除の理由（必須・500文字まで）
  - 削除できない場合（承認済み・承認待ちの有給が賄えなくなる場合）は、確認画面の時点で赤い枠に理由を出し、入力欄とボタンを無効にする。
  - ボタンを押すと、確認ダイアログを出す。
- 送信先は `POST .../removal`（`Admin::Employees::PaidLeaveGrantRemovalsController#create`）。
  - 成功：付与の画面に戻り、「2026/04/01 付与の 10日（2028/04/01 まで）を削除しました。削除の記録は、付与・取得の履歴に残ります。」と出す。
  - 理由が空（空白だけを含む）：422 で確認画面に戻し、上部のメッセージと「削除の理由を入力してください」を出す。付与は残り、記録も作らない。
  - 削除できない場合：422 で、理由（「…のうち 2日 が付与で賄えなくなるため、削除できません。…」）を出す。付与は残り、記録も作らない。
  - 削除済みの付与（二重の削除）：付与の画面に戻し、「この付与はすでに削除されています（管理 太郎・11/26 10:30）。」と出す。記録は最初の1件のまま。
  - 他の従業員の付与・存在しない付与：「指定された付与が見つかりません」と出して、付与の画面に戻す。
  - `GET .../removal`（失敗した後の再読み込みなど）は、確認画面に戻す。
  - 以前の物理削除の `DELETE /admin/employees/:id/paid_leaves/:grant_id` は、ルートを削除したので 404 になる。
- **同時実行**（`PaidLeaveGrantRemoval#save`）
  - 従業員の行をロックした後で、付与を読み直して（`lock`）、次の順に確かめる：削除済みでないこと → 操作する人が有効な管理者であること → 削除すると不足が増えないこと。
  - ロックは、申請（`#submit`）や承認（`ApprovalReview` の `lock_for_review!`）と同じ「従業員の行」。そのため、二重の削除、削除と申請、削除と承認が、入れ違わない。
  - SQLite のロック待ちが上限を超えた場合は、`DatabaseLockError` を捕まえて、エラーメッセージにする（500 にしない）。
- **従業員ロール**は `Admin::BaseController` で拒否する。確認画面を開いても、削除を直接送っても、ホームに戻され「この画面を表示する権限がありません。」と出る。付与は変わらない。

### 削除の記録の表示（履歴）
- 付与・取得の履歴（管理者の付与の画面と、本人の「休暇」画面で共通の `paid_leaves/_history`）に、種類「**付与の削除**」（赤いバッジ）の行を出す。
  - 日付：削除した日
  - 日数：打ち消し線の「+10日」と「残日数に数えません」
  - 内容
    - 「2026/04/01 付与の 10日（有効期限 2028/04/01 まで）を削除しました」
    - 「削除：管理 太郎（2026/11/26 10:30）」
    - 「理由：…」
- 削除した付与の「付与」の行は、履歴にも付与の一覧にも出さない（残日数に数えないため）。
- 付与の画面の一覧の下に「削除した付与が 1件 あります（残日数には数えません。削除の記録は下の履歴にあります）」と出す。
- 残日数のカードで有効な付与が無くなった場合は、「有効な付与はありません（削除した付与は残日数に数えません）。」と出す（削除した付与が無い場合は、今までどおり「まだ付与していません」）。

### 年5日未満の印の対象
- `PaidLeaveAccount#fiscal_year_grants?`：削除されていない付与のうち、使える期間（付与日〜有効期限）が当年度（4/1〜翌3/31）と1日でも重なるものがあるか。
- `PaidLeaveAccount#annual_target_alert?`：`fiscal_year_grants? && below_annual_target?`。役割は見ない。
- 従業員一覧の「5日未満」の印は、`annual_target_alert?` のときだけ付ける。
  - 付与が無いため対象外の人には、印の代わりに薄い文字で「当年度の付与なし」を出す。
  - 一覧の上の説明にも、「当年度に使える有給の付与（付与日〜有効期限が当年度と重なる付与）が無い人には付けません」と書き足した。

## 決めた扱い（仕様に書かれていない点）
| 項目 | 決めた扱い |
|---|---|
| **付与を削除したときの本人への通知** | **送らない**（指示どおり）。本人は「休暇」画面の履歴で、削除と理由を確かめられる。前に届いた「有給休暇が N日付与されました」の通知は、そのまま残る（スプリント16の指摘の「通知の後始末」は、ユーザーの判断で変えていない） |

| 削除できるか判断する時点 | 確認画面を開いたときに一度確かめて（ボタンの無効化）、送信時に、ロックの中で確かめ直す |
| 削除できる人 | 有効な管理者。自分自身の付与も削除できる（付与と同じく、仕様に制限が無いため） |

| 「当年度と重なる」の境目 | 有効期限が 4/1 の付与は重なる（その日に使える）。3/31 の付与は重ならない |
| 一覧の「当年度の付与なし」 | 印が付かない理由が分かるように、付与が無いため対象外の人に薄い文字で出す（無効な従業員も同じ） |

## 既知の問題・懸念
- 開発サーバーと手作業のブラウザでは確かめていない（確かめたのは、システムテストの headless Chrome だけ）。開発 DB は、マイグレーション以外では書き換えていない。
- **開発 DB の山田・次郎の「5日未満」の印が消えた**（付与0件のため。仕様どおり）。今の開発 DB には印が付く人がいないので、確かめるには付与の登録が必要。
- 付与を削除しても、前に届いた「有給休暇が N日付与されました」の通知は残る。押すと `/leaves` に移り、履歴に「付与の削除」が出る。通知の後始末は、ユーザーの判断で変えていない。
- 削除は元に戻せない（付与し直す）。削除した付与は、付与の一覧の表には出さず、履歴にだけ出す。
- 以前の物理削除の URL（`DELETE /admin/employees/:id/paid_leaves/:grant_id`）は 404 になった。古い画面を開いたままの人が「削除」を押した場合は、404 になる（以前の画面では、ボタンが DELETE を送っていたため）。
- 「付与がある」の判定は、日数を見ない。0.5日だけの付与でも、当年度と重なれば印の対象になる（仕様の定義どおり。法令の「年10日以上」の判定はしていない）。
- 付与を数える新しいコードで `PaidLeaveGrant.where` を直接書くと、削除した付与が混ざりうる（`default_scope` にはしていない）。計算の本体（`PaidLeaveLedger`・`PaidLeaveAccount`）では除かれるので、残日数は誤らない。
- スプリント16の評価の軽微な指摘のうち、通知の後始末と夜勤の扱いは、指示どおり変えていない。
