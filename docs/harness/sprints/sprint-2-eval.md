## 受け入れ基準の検証結果
- [x] 管理者は「従業員」画面で一覧（氏名・メールアドレス・役割・雇用区分・状態）を見られる — `admin@example.com` でログインし、ヘッダー「管理 ▾」→「従業員」で `/admin/employees` に遷移。列は「氏名・メールアドレス・役割・雇用区分・入社日・状態・操作」。追加した各ユーザーが正しい値で並び、無効化した花子は「無効」と表示、「無効」タブでは花子だけが表示された。`?status=bogus` は「すべて」として扱われ壊れない。
- [x] 氏名・メール・初期パスワード・役割・雇用区分・入社日を入力して追加できる — 「従業 花子 / hanako@example.com / password123 / 2026-04-01 / 従業員 / パート・アルバイト」で登録 →「従業 花子 さんを登録しました。初期パスワードを本人にお伝えください。」と一覧に表示。2人目の管理者「管理 次郎」も同様に追加。その後どちらもそのアカウントでログインできた。
- [x] 登録済みメールでは追加できずエラー、必須項目が空でも追加できない — メール欄に ` ADMIN@example.com `（大文字・前後空白）で送信 → 422「メールアドレスはすでに登録されています」。required 属性を外して空送信 → 「入力内容を確認してください（4件）」（パスワード・氏名・メールアドレス・入社日）。7文字パスワード → 「パスワードは8文字以上で入力してください」。role に `superuser` を注入 → 「役割は一覧にありません」。連打（ダブルクリック）では1件だけ作成（DB で `double@example.com` が1件）、戻る→同じ内容で再送信は重複エラー。
- [x] 情報（役割を含む）を編集でき、パスワードを再設定できる — 花子の氏名・雇用区分・役割（従業員→管理者）を変更し一覧に反映、元に戻すのも成功。編集でメール空欄 → 422「メールアドレスを入力してください」。パスワード再設定画面で空欄・`abc` はエラー、`resetpass1` で成功 → 旧パスワード `password123` ではログイン不可（共通エラー）、新パスワードでログイン成功。
- [x] 「無効」にでき、無効ユーザーはログインできない（エラー表示）。有効に戻せる — 編集画面の「無効にする」で確認ダイアログ「従業 花子 さんを無効にします。ログインできなくなりますが、よろしいですか？」→ 承諾で「無効」。別ブラウザで正しいパスワードでログイン → 422「このアカウントは無効になっているため、ログインできません。管理者にお問い合わせください。」、誤パスワードなら共通メッセージ。「有効に戻す」後はログインできた。さらに、花子がログイン中に無効化すると次の画面操作でログイン画面へ戻され同じメッセージが出て、再度有効化してもそのセッションは復活しなかった。
- [x] 自分自身の無効化・自分の役割を従業員へ変更できない（最後の管理者の保護） — 自分の編集画面は役割セレクトが `disabled`、「ご自身の役割は変更できません」「ご自身のアカウントは無効にできません」と表示され無効化ボタンなし。DevTools で disabled を外し role=employee で送信 → 422「役割は自分自身では従業員に変更できません」。`DELETE /admin/employees/1/activation` を直接送信 → 「自分自身を無効にすることはできません」で変化なし。さらに次郎で山田を無効化し「次郎だけが有効な管理者」の状態を作り、次郎自身の役割変更・無効化を改ざんリクエストで送っても同じく拒否された。他の管理者の降格・無効化（自分が残る場合）は正しく可能だった。最終的に DB では有効な管理者が2人（id 1, 3）。
- [x] 従業員には管理メニューが出ず、管理 URL の直打ちも拒否される — 花子でログイン時、ヘッダーは「ホーム」「従業 花子」「ログアウト」のみで `/admin` へのリンク 0 件。`/admin/employees`、`/new`、`/1/edit`、`/2/password/edit`、`?status=inactive` を直接開くといずれも `/` に戻され「この画面を表示する権限がありません。」。CSRF トークン付きで POST（作成）・PATCH（自分を管理者に）・DELETE（管理者の無効化）・PATCH（管理者のパスワード再設定）を送っても全てホームへリダイレクトされ、DB は不変（`evil@example.com` は作られず、admin のパスワードも不変）。花子をログイン中に管理者→従業員へ戻すと、次のアクセスで管理画面が拒否された。
- [x] すべてのユーザーが自分のパスワードを変更できる（現在のパスワードが必要） — 花子（従業員）でヘッダーの氏名 → `/password/edit`。現在のパスワード誤り・空欄 → 「現在のパスワードが正しくありません」、確認不一致・3文字・空欄もそれぞれエラー（422）。正しい入力で「パスワードを変更しました。」。管理者が自分の再設定 URL（`/admin/employees/1/password/edit`）を開くと `/password/edit` に誘導される。

## バグ（重要度順）
重大・中のバグはなし。

1. **[軽微]** 「最後の管理者」チェックにロックがなく、同時操作で理論上すり抜け得る
   - 再現手順：有効な管理者 A・B の2人だけの状態で、A が B を、B が A を「ほぼ同時に」無効化（または降格）する。
   - 期待される動作：どちらか一方だけ成功し、有効な管理者が最低1人残る。
   - 実際の動作：未実行（実行すると管理者0人になり、DB 書き換えなしでは復旧できないため）。コード上 `keep_at_least_one_active_admin` は `exists?` で確認してから保存しており、2つのリクエストが並行すると両方が検証を通る可能性がある。実運用で起きる確率は低い。
2. **[軽微]** 存在しない ID（`/admin/employees/9999/edit`）は開発環境の例外画面（404）になる。本番では標準 404 ページになるので実害はないが、「従業員が見つかりません」のメッセージで一覧に戻す方が親切。
3. **[軽微]** 既存管理者は入社日が未設定のまま一覧に「未設定」と出ていた（レポート記載の既知事項）。評価中に次郎の画面から山田の入社日を 2025-04-01 に設定したため現在は解消している。

## 改善点（ジェネレーターへの具体的な指示）
- 役割変更・無効化の保存を `User.transaction` 内で行い、有効な管理者の行を `lock` してから `keep_at_least_one_active_admin` を評価する（同時操作でも管理者が0人にならないようにする）。
- `Admin::EmployeesController` などで `ActiveRecord::RecordNotFound` を rescue し、「従業員が見つかりません。」のアラート付きで `admin_employees_path` にリダイレクトする（任意）。
