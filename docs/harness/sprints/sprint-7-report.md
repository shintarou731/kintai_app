# スプリント 7 実装レポート：打刻修正申請（F7）

## 実装内容

マイグレーションを1つ追加した（新しいテーブルを2つ作るだけで、既存のテーブル・データには触れない）。`bin/rails db:migrate` 済み。開発 DB は ユーザー4・勤怠11・休憩6・設定1 のまま、申請は 0 件。

### データ（F8・F9 を見越した形）
- `approval_requests` テーブル（`db/migrate/20261124190000_create_approval_requests.rb`）＝「申請」の共通の表。
  - **種類は `type` 列（STI）で区別する**：共通部分は `ApprovalRequest`、打刻修正申請は `AttendanceCorrectionRequest`（種類の表示名「打刻修正」）。休暇申請（F9）も `ApprovalRequest` を継承すれば、同じ「申請」一覧・承認画面（F8）に並べられる。
  - 共通の列：申請者・種類・状態・対象日・理由・取り下げ日時・作成日時（＝申請日）。
  - 状態：`pending`（承認待ち）／`approved`（承認済み）／`rejected`（却下）／`withdrawn`（取り下げ）。承認・却下は F8 で使う。取り下げは削除ではなく状態として残す（経緯が分かるように）。
  - 打刻修正の内容：申請する出勤時刻・退勤時刻の列と、休憩は別テーブル `attendance_correction_breaks`（開始・終了とも必須、1申請に複数）。
  - **申請は「その日の勤怠の完成形」を持つ**（出勤・退勤・すべての休憩）。F8 では、この内容で勤怠を置き換えれば「申請内容どおりに更新」できる。比較用に `AttendanceCorrectionRequest#current_attendance`（今の記録）と `#requested_attendance`（申請どおりの勤怠。保存しない `Attendance`）を用意した。
- **重複の防止**：同じ人・同じ種類・同じ対象日の「承認待ち」は1件まで。
  - モデルの検証で防ぐ。
  - 加えて、DB の部分一意インデックス（`status = 'pending'` の行だけが対象）でも防ぐ。同時に2件届いて検証をすり抜けても、2件目は保存されずにエラーになる（`#submit`）。
  - 取り下げた後なら、同じ日に出し直せる。
- **取り下げ**：「承認待ちであること」を条件に1回の UPDATE で書き込む（`ApprovalRequest#withdraw`）。承認・却下と同時に届いても、処理済みの申請が取り下げに変わることはない。

### 入力のルール（`app/models/attendance_correction_request.rb`）
- 時刻は 時:分（`<input type="time">`。全角「０９：００」も可）。退勤と休憩の開始・終了には、それぞれ日付の選択（「11/10(火)」＝当日／「翌日 11/11(水)」）を付けた。
  - これで**日付をまたぐ勤務**（22:00 出勤 → 翌 02:00 退勤）や、日付をまたぐ休憩も入力できる。
  - 出勤は常に対象日の時刻（勤務日＝出勤した日）。
- 入力欄には**今の記録の時刻をあらかじめ入れておく**（直したい所だけ変えればよい）。打刻が全く無い日は空欄で、休憩は空の1行。
- エラーになるもの（すべて画面上部にまとめて表示し、該当する入力欄・休憩の行を赤くする。入力した値は残す）

  | 区分 | エラーになる入力 |
  |---|---|
  | 理由 | 空欄・空白だけ・501文字以上 |
  | 対象日 | 未来の日付（今日は可。JST） |
  | 出勤 | 空欄・形式の誤り・未来の時刻 |
  | 退勤 | 出勤以前（同時刻も不可。「翌日を選んでください」と案内）・出勤から24時間超・未来の時刻・日付の値が当日／翌日以外（直接送信） |
  | 退勤の空欄 | 過去の日はエラー。ただし、まだ勤務中でありうる勤務（出勤から24時間以内で、今の記録でも退勤していない）は空欄にできる。画面に「勤務中なら空欄」と表示する |
  | 休憩 | 開始・終了の片方だけ・終了が開始以前・勤務時間（出勤〜退勤、退勤が空欄なら現在まで）の外・未来・休憩どうしの重なり・11回以上。メッセージは「休憩2と休憩3の時間が重なっています」のように行番号付き。境目が接するだけ（12:00〜13:00 と 13:00〜13:15）は可 |
  | 前日・翌日との重なり | 前日の勤務の退勤より前の出勤、翌日の勤務の出勤より後の退勤 |
  | 今の記録と同じ内容 | 「今の記録と同じ内容です」（秒は切り捨てて比べる） |
  | 重複 | 同じ日に承認待ちの修正申請がある |

### 画面
- **ナビに「申請」**を追加（勤怠履歴の右。申請一覧・詳細・入力画面で選択状態になる）。ホームの「アカウント」にも「申請の一覧を見る」。
- **申請一覧** `GET /requests`
  - 自分の申請だけを新しい順に表示する。列は 対象日・種類・内容（「出勤 09:00／退勤 翌 02:00／休憩 2回」）・申請日・状態・詳細。
  - 状態は色付きのバッジ：承認待ち＝黄、承認済み＝緑、却下＝赤、取り下げ＝グレー。
  - 「すべて／承認待ち」のタブ（件数付き）。
  - 上部に「対象日を選んで打刻修正を申請する」フォーム（日付は今日まで）。
  - 申請直後は、その行を色付きで強調する。
  - 375px では縦積みのカード表示になる。
- **打刻修正申請の入力** `GET /requests/corrections/new?date=2026-11-10`、送信は `POST /requests/corrections`
  - 「今の記録」カード（退勤漏れなら赤い印）と、入力フォーム（出勤・退勤・休憩・理由）。
  - 休憩は「＋ 休憩を追加」「削除」で行を増減できる（最大10行、番号は自動で振り直す。Stimulus：`app/javascript/controllers/break_rows_controller.js`）。
  - 入力画面を出さずに戻す場合
    - 未来の日付：その月の勤怠履歴へ戻し「未来の日付（11/25(水)）は修正申請できません」。
    - 日付として読めない値：申請一覧へ戻す。
    - すでに承認待ちの申請がある日：その申請の詳細へ戻し「すでに承認待ちの修正申請があります。…取り下げてから出し直してください」。
  - 直接送信した場合も同じ判定をする。パラメーターが欠けていても 400 にはならない。
  - 申請すると申請一覧へ移り、「11/10(火) の打刻修正を申請しました（承認待ち）。承認されるまで勤怠記録は変わりません。」と表示する。
- **申請の詳細** `GET /requests/:id`
  - 種類・対象日・申請日時・状態（取り下げなら取り下げ日時）を表示する。
  - 「今の記録」と「申請内容」の比較表（出勤・退勤・休憩・実働時間）。変わる行には色と「変更」の印を付ける。
  - 理由（改行を保持）。
  - 承認待ちなら「この申請を取り下げる」（確認ダイアログあり）と「勤怠履歴で見る」。取り下げ済みなら「この日の修正申請を出し直す」。承認・却下済みなら「処理済みの申請は取り下げできません」。
- **取り下げ** `POST /requests/:id/withdrawal`
  - 本人の承認待ちの申請だけ取り下げられる。承認済み・却下・取り下げ済みは「『承認済み』のため、取り下げできません（取り下げられるのは承認待ちの申請だけです）」で、状態は変わらない。
- **他人の申請**
  - 一覧に出ない。詳細・取り下げを URL 直打ちや直接送信で試しても「指定された申請が見つかりません」で一覧へ戻す（存在するかどうかも明かさない）。
  - 申請者は常にログイン中の本人で、`user_id` を送っても無視する。
- **勤怠履歴**
  - 表の右端に「修正」列を追加した。今日までの日は「修正申請」リンク、承認待ちの日は黄色の「申請中」バッジ（申請の詳細へ）。未来の日は空欄。
  - 凡例に「申請中＝承認待ちの修正申請あり」を追加した。
  - 375px では日付と同じ段の右端に表示する（勤務の無い日にも出る）。
  - 承認されるまで記録はそのまま（退勤漏れの印なども変わらない）。
- **退勤漏れの導線**
  - 勤怠履歴：「管理者に連絡してください」を「修正申請で、実際に退勤した時刻を申請してください」に変え、日ごとに「11/10(火) の修正申請」リンクを付けた（申請中なら「11/10(火) は申請中」→ 申請の詳細）。
  - ホームのお知らせ：同じ文言に変え、「11/10(火) の修正申請をする」（申請中なら「は申請中」）のリンクを付けた。
  - 夜勤中の「退勤漏れ」表記は変更していない（ユーザー確認待ちのため）。

### スプリント6評価の軽微な指摘
1. **375px で「締め日ごとの範囲」表の「〜」が切れる**：修正した。
   - 表を縦積みのカード表示（`table--responsive`、各欄に「月度」「期間」の見出し）にした。
   - 原因の一つは、スマートフォン幅で `.card { padding: 18px }` が `.card--flush { padding: 0 }` を上書きしていたこと（既存の CSS の不具合）。`.card--flush` は 375px でも余白 0 を保つようにした。従業員一覧・勤怠履歴の表も、375px ではカードの端まで使うようになる。
   - システムテストに「表の中の要素・文字の右端がカードの右端を超えない」確認を足した。
2. **`work_rule_setting` パラメーターを欠いた PATCH が 400 になる**：修正した。設定の項目を含まない（または値がハッシュでない）リクエストは、設定画面を 422 で表示し、上部に「保存する内容が送信されませんでした。入力欄に値を入れて「保存する」を押してください。」と出す。DB は変わらない。

## 動作確認の方法

- 起動：`bin/rails server -p 3000`
  - マイグレーションは適用済み。未適用なら `bin/rails db:migrate`（新しいテーブルを作るだけで、既存データは変わらない）。
- ログイン：従業員 `double@example.com` / `password123`、管理者 `admin@example.com` / `password123`。
- 画面
  - 申請一覧：ヘッダー「申請」、または `http://localhost:3000/requests`
  - 勤怠履歴：`http://localhost:3000/attendances`（10月は `?month=2026-10`）
  - 入力画面：`http://localhost:3000/requests/corrections/new?date=2026-11-10`
- 確認手順（double、実時刻 11/24 を想定）
  1. ホームの「退勤漏れの勤務があります」に「修正申請で、実際に退勤した時刻を申請してください」と、日ごとの「…の修正申請をする」リンクがある（開発 DB の double は 11/10 と 10/30 が退勤漏れ）。
  2. 勤怠履歴（11月）の右端「修正」列に、11/1〜11/24 は「修正申請」が出て、11/25 以降は空欄。退勤漏れのお知らせに「11/10(火) の修正申請」リンクがある。
  3. 11/10 の「修正申請」を開く。
     - 「今の記録」に出勤 10:00・退勤 未打刻（退勤漏れ）が出て、出勤欄に 10:00 が入っている。
     - 退勤を空欄・理由を空欄で送ると、エラーになり欄が赤くなる。理由の空欄はブラウザの必須チェックで止まるため、サーバー側のエラーを見るには、開発者ツールで required を外すか、退勤だけ誤った値で送る。
     - 退勤を「当日 09:00」で送ると「退勤時刻は出勤時刻より後に…『翌日』を選んでください」。
     - 休憩を「＋ 休憩を追加」で2行にし、12:00〜13:00 と 12:30〜12:45 で送ると「休憩1と休憩2の時間が重なっています」。
     - 休憩を 9:00〜9:30（出勤前）で送ると「勤務時間（10:00〜…）の中に」のエラー。
     - 日付をまたぐ入力：退勤の日付を「翌日 11/11(水)」、時刻 02:00 にすると受け付けられる（11/11 には勤務が無い）。
     - 前日・翌日との重なり：11/20 の修正申請で、退勤を「翌日 11/21(土)」の 10:00 にすると、「退勤時刻が翌日（11/21(土)）の勤務の出勤（09:00）より後です」になる。11/24 で出勤を 01:00 にすると、前日 11/23 の夜勤（翌 02:00 退勤）と重なるエラーになる。
  4. 正しい値（例：退勤 当日 19:00、理由「退勤の打刻を忘れました」）で申請すると、申請一覧に「承認待ち」で強調表示される。履歴の 11/10 に「申請中」（退勤漏れの印はそのまま＝記録は変わらない）。ホームのお知らせは「11/10(火) は申請中」。
  5. もう一度 `…/new?date=2026-11-10` を開くと、既存の申請の詳細へ戻され「すでに承認待ちの修正申請があります」と出る。
  6. 詳細で「今の記録／申請内容」の比較表（退勤・実働時間の行に「変更」）を確認し、「この申請を取り下げる」→ 確認 → 状態が「取り下げ」になり、「この日の修正申請を出し直す」が出る。
  7. 未来の日：`…/new?date=2026-11-25` は勤怠履歴へ戻され「未来の日付（11/25(水)）は修正申請できません」。今日 `…/new?date=2026-11-24` は開ける（double は今日の記録が無いので退勤に「勤務中なら空欄」）。

## 既知の問題・懸念

- **承認・却下の処理は未実装（F8）**。`approved`／`rejected` の状態と、比較表・`requested_attendance` は用意した。承認者・処理日時・コメントの列は F8 で追加する想定で、まだ無い。
- **退勤を空欄にした申請（勤務中の当日）**：F8 で承認すると、退勤なしの勤怠になる。
  - 承認が遅れて出勤から24時間を過ぎると、再び退勤漏れになる。
  - 申請中に本人がホームで出勤を打刻すると、承認時には今の記録と申請の両方がある状態になる。
  - F8 での扱い（承認時に今の記録を上書きする、休憩中の休憩をどうするか）は F8 で決める必要がある。
- **休憩中（終了していない休憩）は申請できない**：申請の休憩は開始・終了とも必須。
- **勤怠記録を「削除」する申請（誤って出勤した日を無かったことにする）は扱っていない**：出勤は必須。
- 前日・翌日の勤務との重なりは、勤怠記録とだけ比べている。隣の日の「承認待ちの申請」とは比べないため、承認の順番によっては重なりうる（F8 の承認時に再確認するのが望ましい）。
- 月度の締め（F14）による申請の制限はまだ無い（F14 で追加）。
- 勤怠履歴の全行に「修正申請」リンクが出るため、表がやや賑やかになった。
- 日付の選択肢は「当日／翌日」の2つだけ。出勤から24時間以内の勤務なら、これで足りる。
- `.card--flush` の 375px の余白を 0 に直したことで、従業員一覧・勤怠履歴の表も 375px で少し広くなった（既存のシステムテストはすべて成功）。
