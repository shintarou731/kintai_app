# スプリント 8 実装レポート：承認（管理者）（F8）

## 実装内容

マイグレーションを1つ追加し、`bin/rails db:migrate` まで実行した（`db/migrate/20261124210000_add_review_columns_to_approval_requests.rb`）。
- 中身は `approval_requests` に列を足すだけ。既存の行の値は変わらない。
- 開発 DB の件数は、適用後もユーザー4・勤怠11・休憩6・設定1・申請7（承認待ち3／取り下げ4）のまま。

### データ
追加した列（`approval_requests`）

| 列 | 意味 |
|---|---|
| `reviewer_id` | 処理した管理者（users への外部キー） |
| `reviewed_at` | 処理日時 |
| `review_comment` | 管理者のコメント（却下時は必須、500文字まで） |
| `reviewed_record` | 処理した時点の勤怠記録（JSON）。承認した後も「承認前の記録」と申請内容を比べるために残す |

### 承認・却下の処理（`app/models/approval_review.rb`）
- 承認・却下は `ApprovalReview#save` で行う。1つのトランザクションの中で、次の順に処理する。
  1. 申請を DB から読み直す。
  2. 処理できるかを確かめる。
     - 処理する人が「有効な管理者」であること。
     - 申請が承認待ちであること。
     - 自己承認ルールに反しないこと。
     - 承認の場合は、承認できない理由（後述）が無いこと。
  3. 状態・処理者・処理日時・コメント・処理時点の記録を保存する。
  4. 承認なら、勤怠記録を更新する。
- 途中で失敗すると全部取り消す。申請は承認待ちのまま、勤怠も変わらない（テストで確認済み）。
- 種類ごとの処理は、サブクラスのフックに分けた（`approval_blockers` / `apply_approval!` / `review_snapshot` / `approval_result_note` / `detail_associations`）。
  - F9 の休暇申請も、`ApprovalRequest` を継承してフックを書けば、同じ承認画面・同じ処理に乗る。
  - 承認画面の「対象日」欄はヘルパー `approval_request_target_label` を通している。休暇の期間表示はここで差し替えられる。

### 承認で勤怠を更新する（`AttendanceCorrectionRequest#apply_approval!`）
- 申請は「その日の勤怠の完成形」なので、出勤・退勤・休憩を申請どおりに置き換える。
  - 勤怠が無い日は新しく作る。
  - 休憩は、申請に無いものを削除し、申請の休憩を作る。これで追加・削除・変更がすべて反映される。

### 自己承認ルール（`ApprovalRequest#self_review_status`）
- 「有効な管理者」＝役割が管理者で、状態が有効なユーザー（`User.active_admins`）。無効化された管理者と従業員は数えない。

  | 状態 | 条件 | 動作 |
  |---|---|---|
  | `:not_own` | 他人の申請 | 通常どおり処理できる |
  | `:allowed` | 自分の申請、有効な管理者が1人 | 自分で承認・却下できる。処理者として本人の氏名と日時が記録される |
  | `:forbidden` | 自分の申請、有効な管理者が2人以上 | 操作は表示しない。直接送信しても拒否し、承認待ちのまま |

- 人数は画面を表示するたびに数え直す。処理の直前にも、トランザクションの中で数え直す。管理者の追加・無効化の直後から、表示と動作が切り替わる。

### 申し送りへの対応
1. **承認時の再検証**：承認する直前に、その時点の記録で確かめ直す（`approval_blockers`）。承認できない場合は理由を表示する。
   - 確かめる内容
     - 前日の勤務の退勤より前に出勤する内容になっていないか。
     - 翌日の勤務の出勤より後に退勤する内容になっていないか。
     - 退勤が空欄の申請なのに、翌日に勤務の記録がないか。
     - 退勤を残す場合に、出勤から24時間を超えないか。
   - 隣の日の別の申請を先に承認して重なった場合も、勤怠記録と比べるので拒否される。
   - 詳細画面では、理由の一覧を「このままでは承認できません」として表示し、「承認する」ボタンを押せなくする（却下はできる）。直接送信しても 422 で理由が出る。
2. **退勤を空欄にした（勤務中の）申請の扱い**：「申請した時点までの内容」として扱うことにした。
   - 出勤と、申請した休憩は申請どおりにする。
   - 申請した後にホームで打刻した退勤・休憩（休憩中の休憩も含む）は、そのまま残す。
   - まだ退勤していなければ、退勤なし（勤務中）のまま。ホームから退勤できる。
   - 詳細画面に「退勤が空欄（勤務中）の申請です」という注意を出し、承認後の退勤がどうなるかを書く。
     - 例：「退勤は今の記録（18:00）のまま残ります」「退勤は未打刻のまま（勤務中）になります」。
     - 出勤から24時間を過ぎていれば「承認後は退勤漏れになります」も添える。
   - 承認後のメッセージは「勤怠記録の出勤・休憩を申請内容どおりに更新しました（退勤は今の記録のままです）」。
   - 申請した後に今の記録が変わった場合は、どの申請でも「申請した後に、勤怠記録が変わっています」と注意を出す。
3. **同時送信による `SQLite3::BusyException`（500）**：3段構えにした。
   - `config/database.yml` に `default_transaction_mode: immediate` を追加した。
     - 書き込むトランザクションは、開始時に書き込みロックを取って順番待ちする。
     - 一時 DB で8スレッド同時に「読む→書く」を試した。DEFERRED では BusyException が出て、IMMEDIATE では0件だった。
   - `config/initializers/sqlite_lock_wait.rb` を追加した。
     - ロック待ちの間も他のスレッドが動けるようにする（`busy_handler_timeout=`。Rails 8 と同じ方式）。
     - 従来の busy_timeout は、待つ間 Ruby の他のスレッドを止めてしまう。
   - それでもロックが取れない場合（`DatabaseLockError` で判定）は、例外にしない。
     - 申請（`submit`）：入力画面にエラーを出す。
     - 承認・却下（`ApprovalReview`）：詳細画面にエラーを出す。
     - 取り下げなど、その他の書き込み：`ApplicationController` の `rescue_from` で元の画面に戻し、「他の操作と同時に処理されたため、完了できませんでした…」と出す。
   - 実際にスレッドを並べたテストで確かめた（`test/models/approval_concurrency_test.rb`）。
     - 申請6件の同時送信：1件だけ作られ、例外0件。
     - 承認6件の同時送信：1件だけ成功し、勤怠も1件。
     - 承認3件と取り下げ3件の同時送信（3回）：成功は1件だけで、状態と勤怠が食い違わない。
   - IMMEDIATE を一時的に外して同じテストを流すと、承認の同時送信でロック競合が起きた。例外にはならず、メッセージとして返った（多段の対策が効いている）。

### 画面
- **ナビ**
  - 管理メニューの先頭に「承認」を追加し、承認待ちの件数バッジ（赤）を付けた。
  - メニューを閉じていても分かるように、「管理」の横にも同じ件数を出す。0件なら出さない。
  - ホームの「アカウント」に「申請を承認する（承認待ち N件）」を追加した。
- **承認の一覧** `GET /admin/approvals`
  - 「承認待ち／処理済み」のタブ（件数付き）。
  - 承認待ち
    - 列は 申請者・種類・対象日・内容・申請日。申請日の古い順に並ぶ。
    - 自分の申請には「あなたの申請」の印を付ける。
    - 自己承認できない申請のボタンは「詳細」、処理できる申請は「確認する」。
    - 一覧の上に、自己承認ルールの案内を出す（自分の申請があるときだけ）。
  - 処理済み：上の列に加えて 結果・処理した管理者・処理日時。処理日時の新しい順に並ぶ。
  - 375px ではカード表示になる。
- **承認の詳細** `GET /admin/approvals/:id`
  - 申請者・種類・対象日・申請日時・状態を表示する。
  - 比較表は「今の記録」と「申請内容」を並べる。変わる行には色と「変更」の印を付ける（申請者の画面と同じ部品）。
  - 申請の理由を表示する。
  - 承認・却下のフォーム
    - コメント欄は「却下するときは必須」、500文字まで。
    - 「承認する」「却下する」ボタンにはどちらも確認ダイアログがある。
    - 却下でコメントが空なら 422 で「コメントを入力してください（却下するときは…）」。
  - 自分の申請の表示
    - 有効な管理者が2人以上：「ご自身の申請は他の管理者が処理します」と出し、フォームを出さない。
    - 1人：「管理者が1名のため、ご自身の申請を承認・却下できます」と出し、フォームを出す。
  - 処理済み・取り下げの申請：フォームの代わりに状態を説明する。処理済みなら「処理結果」（処理者・日時・コメント）を出す。
  - 処理が終わると承認の一覧（承認待ち）に戻り、「〇〇 さんの 11/20(金) の打刻修正申請を承認しました。勤怠記録を申請内容どおりに更新しました。」と出す。
- **申請者の「申請」画面**
  - 一覧
    - 状態の下に、処理者・処理日時とコメント（40文字まで）を出す。
    - タブに「処理済み」を追加した。
  - 詳細
    - 「処理結果」カード：結果・処理した管理者・処理日時・コメント（改行を保つ。無ければ「（コメントなし）」）。
    - 比較表は、処理済みなら処理した時点の記録と比べる。見出しは「承認前の記録」「却下時の記録」。
  - 承認・却下済みの申請には取り下げボタンを出さず、「処理済みの申請は取り下げできません」と表示する（F7 で保留だった画面確認ができる）。
  - 却下された申請には「この日の修正申請を出し直す」を出す。
- 権限のない人のアクセス
  - 従業員は `/admin/approvals` に入れない（既存の管理画面と同じく、ホームへ戻して「権限がありません」）。
  - 存在しない申請 ID は、承認の一覧へ戻して「指定された申請が見つかりません」。

## 既知の問題・懸念

- **`config/database.yml` の変更（IMMEDIATE トランザクション）はアプリ全体に効く**。打刻など他の書き込みも、開始時に書き込みロックを取るようになった。既存のテスト（system を含む）はすべて成功した。読み取りだけのトランザクションでも書き込みロックを取るため、利用者が多いと待ちが増えうる（数十名規模なら問題ない想定）。
- **`config/initializers/sqlite_lock_wait.rb` は Rails 7.2 の SQLite アダプタの非公開メソッド（`configure_connection`）を上書きしている**。Rails 8 に上げたら不要になるので削除すること。
- `ApplicationController` の `rescue_from DatabaseLockError` は、GET では例外のまま（画面の表示で書き込みは無いので、起きない想定）。
- 承認は管理メニューの中にある（仕様のデザインどおり）。件数は「管理」の横にも出るが、メニューを開くまで「承認」の項目そのものは見えない。
- 承認の一覧・処理済みの一覧に件数の上限やページ分けは無い。数十名規模なら問題ないが、処理済みは増え続ける。
- 承認すると勤怠の秒は 0 になる（申請は 時:分 で入力するため）。打刻の秒は残らない。
- 退勤が空欄の申請を承認したとき、出勤から24時間を過ぎていれば退勤漏れの勤務になる（画面で予告する）。承認は止めていない。止めるかどうかは運用次第。
- 申請者が無効化されていても承認・却下はできる（詳細に「無効」の印を出す）。
- 管理者が他の従業員の勤怠履歴を直接見る画面は無い（F14 の範囲）。承認後の反映は、従業員でログインして確認する必要がある。
- `AttendanceCorrectionRequest` が約 470 行になった。検証（F7）と承認（F8）を別の部品に分けるのが望ましい（今回は既存の構造に合わせた）。
- 開発サーバー＋Playwright での目視確認はしていない。
