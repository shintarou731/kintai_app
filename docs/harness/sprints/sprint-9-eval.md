# スプリント 9 評価：休暇申請（F9）

## 判定：不合格

F9 の受け入れ基準 7 件は、すべて画面操作で満たしていることを確認した。スプリント8の指摘 4 件も直っていた。
それでも不合格にした理由は、**コード品質が閾値 7 を下回る（6 点）**ため。

- `bin/rails test` が**一定の確率で失敗する**。
  - 原因は新規テスト `test/models/leave_concurrency_test.rb` の 1 件目。
  - テストの前提が間違っている。アプリの不具合ではない（下の「バグ1」に原因の調査結果を書いた）。
  - 共通ルールの「`bin/rails test` が通ること」を安定して満たせない。
  - 実装レポートは「1件だけ作られ、例外0件（直列化の確認）」と書いているが、このテストはその性質を正しく確かめていない。
- あわせて、375px で「管理」メニューが画面の右にはみ出す UI バグ（中）がある。ナビが5項目になったことで新たに起きた。

**修正の量は小さい**。テストの期間をすべて共通の1日を含むように直し、ドロップダウンの位置を直せばよい。

検証の環境
- 開発サーバー：`bin/rails server -p 3000`。`DEV_NOW` は使っていない。実日付 2026-11-25（水）00:11〜00:25 JST。
- ブラウザ操作：Playwright MCP。
- DB の確認：`bin/rails runner`（読み取りのみ）。

## バグ（重要度順）
1. **[中] 新規の並行実行テストが前提を誤っており、`bin/rails test` がときどき失敗する**
   - 再現手順
     - `bin/rails test test/models/leave_concurrency_test.rb` を繰り返し実行する。25 回中 5 回失敗した。
     - 全体の `bin/rails test` では、6 回中 1 回失敗した。
   - 期待される動作：毎回成功する。
   - 実際の動作：`LeaveConcurrencyTest#test_開始日の違う、期間の重なる休暇を同時に送っても…` が `leave_concurrency_test.rb:57` で失敗する（Expected: 1 / Actual: 4、または 3）。
   - 原因の調査（テスト DB で、SQLite の `trace` を使って実際の SQL を記録した）
     - 各スレッドは `begin immediate transaction` で正しく1つずつ実行されていた。それぞれの SELECT は、前のスレッドの commit の後に走っていた。**アプリの直列化は正しい。**
     - 6 つの期間 `[0,4] [1,1] [2,3] [0,0] [3,4] [2,2]` は、コメントでは「どれも互いに重なる」とされている。しかし実際には、`[1,1]`（火）・`[0,0]`（月）・`[2,2]`（水）・`[3,4]`（木〜金）は互いに重ならない。
     - そのため、短い期間が先にロックを取ると、正当に最大 4 件が作られる。`[0,4]` が先に通ったときだけ 1 件になり、成功する。
   - 影響
     - CI や開発者のテストが不安定になる。
     - 「互いに重なる申請は同時でも1件だけ」という性質を、このテストでは確かめられていない。
2. **[中] 375px で「管理」メニューが画面の右にはみ出す（ナビが5項目になったことによる新しい問題）**
   - 再現手順：admin で 375px 幅にして、ヘッダーの「管理」を押す。
   - 期待される動作：メニューが画面内に収まり、「承認」の件数バッジが見える。
   - 実際の動作
     - `.nav__menu-list` が left 262px〜right 442px に表示され、`scrollWidth` が 442 になる（横スクロールが出る）。
     - 「承認」の右にあるバッジ（5）が画面外に切れて見えない（`.playwright-mcp/s9-admin-menu-375.png`）。
     - メニューを閉じた状態でも、この要素は画面外に配置されている。
3. **[軽微] 過去の開始日を選ぶと、終了日の初期値（今日）が残り、意図しない複数日の申請になりやすい**
